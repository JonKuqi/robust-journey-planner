# RobustJourneyPlanner — Implementation Reference

`src/routing/robust_journey_planner.py`

---

## 1. Problem statement

The planner answers queries of the form:

> "I must arrive at stop B by 18:00. Which departure from stop A gives me the latest start while still having at least 75% confidence of arriving on time?"

Standard timetable planners optimise for schedule only. This planner adds a second axis: the empirical probability that each vehicle connection arrives before the next one departs, estimated from the XGBoost delay model. Routes that are scheduled to arrive on time but have unreliable connections are deprioritised in favour of earlier, more robust options.

---

## 2. Two-phase lifecycle

The planner separates **cold work** (done once per region / travel date) from **hot work** (done per query).

```
prepare()                          plan()
─────────────────────────────      ──────────────────────────────
Build Trino CSA tables             Binary-search the connection window
Fetch stops, footpaths,            Run backward profile CSA scan
  connections from Trino           Propagate log-confidence per connection
Materialise struct-of-arrays       Insert into Pareto profiles
Bake per-connection quantiles      Early-stop when enough routes found
Load XGBoost models (fallback)     Reconstruct steps from profile pointers
                                   Annotate confidence + robust times
                                   Return up to max_routes routes
```

After `prepare()` the planner holds everything in RAM. `plan()` does zero Trino calls, zero disk reads, and zero model inference (all quantiles are pre-baked).

---

## 3. prepare() — what gets built

### 3.1 Struct-of-arrays: `conn[day]`

The raw connection DataFrame is split into five parallel flat lists, one per weekday:

```python
conn[day] = {
    "dep_stop":  [int, ...],   # departure stop id
    "arr_stop":  [int, ...],   # arrival stop id
    "dep_secs":  [int, ...],   # departure time in seconds from midnight
    "arr_adj":   [int, ...],   # arrival time in seconds (next-day trips get +86400)
    "trip_idx":  [int, ...],   # integer trip index into trip_meta_by_idx
}
```

Sorted by `dep_secs` so binary search (`bisect`) can slice any time window in O(log n).

The alternative of keeping rows as tuples or dataframe rows would touch ~3× more memory per connection and trigger Python attribute lookup overhead in the hot loop.

### 3.2 Trip metadata

```python
trip_meta_by_idx[k] = {
    "trip_id": str,
    "line_text": str,
    "operator_id": str,
    "transport": str,
}
```

Indexed by integer `trip_idx`. Route reconstruction calls `trip_meta_by_idx[trip_idx_a[i]]` — one list read, no string hash.

### 3.3 Footpaths

```python
footpaths[stop_id] = [(neighbour_id, walk_secs, dist_m), ...]  # sorted by dist_m
footpath_dist[(a, b)] = float   # metres
footpath_secs[(a, b)] = int     # seconds
```

Sorted by `dist_m` so the walk loop can `break` as soon as `dist > max_walk_m` — no need to scan the full neighbour list.

### 3.4 Baked quantiles: `conn[day]["quantiles"]`

When `prepare(travel_date=..., load_delay_lookup=True)` is called, a fifth array is added:

```python
conn[day]["quantiles"] = [list[float] | None, ...]   # parallel to the other arrays
```

Each entry `quantiles_a[i]` is the pre-looked-up delay quantile list for connection `i` on that date — e.g. `[45.0, 67.2, 89.4, 112.0, 130.0, 158.0, 210.0]` for quantile levels `(0.50, 0.60, 0.70, 0.80, 0.85, 0.90, 0.95)`.

The hot loop reads `quantiles_a[i]` once and reuses it for both headway evaluations (tau1 and tau3). Zero dict lookups, zero string construction per connection.

How the baking works:

1. Load the per-date delay file (`artifacts/precomputed_day_delay/{date}/delays.json`) generated by `DayDelayGenerator`. Keys are `"{arr_stop}__{LINE_TEXT}__{hour}"` — 3 fields, with `line_text` always uppercased at generation time.
2. One O(n) pass over `conn[day]`: for each connection build the 3-field key and look up the quantile list.
3. Any connection not in the day-delay file is resolved by a batch XGBoost inference call at `prepare()` time. After this pass, every entry in `quantiles_a` is a `list[float]` — no `None` values during the scan.

## 4. Delay lookup hierarchy

When `_delay_quantiles_for_step` is called (during post-scan annotation only, not in the hot loop):

```
1. day_delay_lookup (3-field: arr_stop__LINE_TEXT__hour)
        ↓ miss
2. delay_lookup (6-field: bpuic__line_text__hour__dow__month__day_type)
        ↓ miss
3. delay_fallback_lookups[0] (bpuic, line_text, hour)
        ↓ miss
4. delay_fallback_lookups[1] (bpuic, line_text)
        ↓ miss
5. return None → predicted_delay_sec = 0.0
```

The 6-field precomputed lookup is loaded at `prepare()` time by merging per-district JSON files:

```python
for uuid in region_uuids:
    district_path = artifacts.for_region([uuid]).precomputed_delays_json_path()
    if district_path.exists():
        merged.update(json.load(district_path))
```

Each district file is ~5 MB (generated once by `build_all_region_precomputed_delays`). Merging n districts is O(n) with no regeneration needed for any combination.

## 5. The profile CSA scan

### 5.1 Window setup

```python
deadline_secs  = time-of-day of arrival_deadline, in seconds from midnight
earliest_dep   = deadline_secs - search_window_minutes * 60
start_idx      = bisect_left(dep_secs_list, earliest_dep)
end_idx        = bisect_right(dep_secs_list, deadline_secs) - 1
```

The scan runs backward: `i` starts at `end_idx` and decrements to `start_idx`.

### 5.2 Data structures

```python
# Per-trip labels — updated as the scan moves backward
T_arr[ti]       = float    # best (earliest) arrival reachable while on trip ti
T_exit[ti]      = int      # connection index where ti alights for that arrival
T_kind[ti]      = byte     # _KIND_WALK (1) or _KIND_XFER (2)
T_log_conf[ti]  = float    # accumulated log-confidence for that path; 0.0 = log(1.0)

# Per-stop Pareto profiles — built up during the scan
pdep[stop]  = [dep_secs, ...]   # sorted ascending departure seconds
pent[stop]  = [(arr, board_conn_idx, exit_conn_idx, kind, log_conf), ...]
              # co-indexed with pdep; latest departure → lowest index
```

### 5.3 Per-connection logic (the hot loop)

For each connection `i` (backward order), the scan evaluates three ways of using it:

**tau1 — alight and walk to the destination**

```
headway  = deadline_secs - arr_adj[i] - walk_secs_to_dest
p1       = P(delay ≤ headway)          # interpolated from quantiles_a[i]
lc1      = log(p1)
tau1     = arr_adj[i] + walk_secs      if lc1 >= log_q  else INF
```

**tau2 — stay seated on the same trip**

```
tau2 = T_arr[ti]
lc2  = T_log_conf[ti]
```

No probability update here — the trip label already encodes the full downstream confidence.

**tau3 — alight and transfer to another connection**

```python
k        = bisect_left(pdep[arr_stop], arr_adj[i] + min_transfer)
next_dep  = pdep[arr_stop][k]
headway  = next_dep - arr_adj[i] - min_transfer
p3       = P(delay ≤ headway)
lc3      = log(p3) + pent[arr_stop][k][4]   # chain downstream log-conf
tau3     = pent[arr_stop][k][0]              if lc3 >= log_q  else INF
```

**Selection and update**

```python
if tau2 <= tau1 and tau2 <= tau3:
    # stay seated — no new label needed, just inherit trip state
elif tau1 <= tau3:
    # walk to destination wins
else:
    # transfer wins

if tau_c < T_arr[ti] and lc >= log_q:
    T_arr[ti]      = tau_c
    T_exit[ti]     = ex
    T_kind[ti]     = kind
    T_log_conf[ti] = lc
```

The trip label is updated only when the new path is **strictly better** (earlier arrival) **and** passes the confidence gate. This means the trip label always represents a reachable, confidence-passing path.

**Profile insert**

If the connection reached the destination (tau_c < INF), both the departure stop and any walkable neighbours are inserted into their Pareto profiles:

```python
prof_insert(pdep, pent, dep_stop, dep_secs, tau_c, board, exit, kind, lc)
for nb, wsecs, dist in footpaths[dep_stop]:
    if dist > max_walk_m: break
    prof_insert(pdep, pent, nb, dep_secs - wsecs, tau_c, board, exit, kind, lc)
```

### 5.4 Confidence propagation — why log-space is exact

Route confidence is the product of per-leg probabilities:

```
C = p₁ × p₂ × ... × pₖ
```

In log space this is a sum:

```
log C = log p₁ + log p₂ + ... + log pₖ
```

Each `log pᵢ ≤ 0`, so chaining more legs can only decrease (or maintain) log-confidence. This makes the gate exact: if the downstream portion of a path already has `log_conf < log_q`, adding any upstream leg can only make it worse. The admission gate `lc >= log_q` applied at each connection is therefore a strict sufficient filter with no false negatives.

### 5.5 Probability interpolation — `_p_leq_headway`

```python
@staticmethod
def _p_leq_headway(quantiles: list[float], levels: tuple, headway: float) -> float:
```

Given stored quantile points `(q₀, q₁, ..., q₆)` at probability levels `(0.50, 0.60, ..., 0.95)`:

- If `headway ≤ q₀`: linear interpolation from 0 to `levels[0]` over `[0, q₀]`.
- If `qₖ₋₁ < headway ≤ qₖ`: linear interpolation between `(levels[k-1], levels[k])`.
- If `headway > q₆`: return 1.0.

This is a piecewise linear CDF approximation. The interpolation is done inline with a simple forward scan over the 7 quantile points — no allocation, no sorting, no attribute lookup.

### 5.6 Pareto dominance — `_prof_insert`

A label `(dep, arr)` dominates an existing label `(dep', arr')` if `dep >= dep'` and `arr <= arr'` (depart no earlier, arrive no later). The profile keeps only non-dominated labels.

Profiles are stored sorted by `dep_secs` ascending. The insert:

1. Binary-search for `dep` to find position `pl`.
2. If an existing label at `pl` already has `arr ≤ new_arr`, the new label is dominated — skip.
3. Otherwise, find the range `[lo, pr)` of labels dominated by the new one and replace them all with a single splice: `ds[lo:pr] = [dep]`, `es[lo:pr] = [(arr, ...)]`.

Because profiles are kept sorted and arrivals are monotonically ascending (non-dominated set), the bisect calls are O(log p) and the dominance sweep is amortised over the lifecycle of the profile.

## 6. Early stopping

```python
if check_early_stop:
    src_dep = pdep.get(start_stop_id)
    if src_dep and len(src_dep) >= max_routes + 2 and d_secs < src_dep[0]:
        break
```

`check_early_stop` is set when the departure stop of the current connection (or a footpath neighbour) is the query source stop. Once the source profile has `max_routes + 2` entries **and** the scan position is earlier than the earliest profile entry, scanning further back can only produce departures that would be dominated in the profile — so nothing can improve the output. The scan breaks immediately.

This gives roughly a **4× speed-up** in practice because most queries saturate the profile well before the full search window is exhausted.

## 7. Route reconstruction

After the scan, routes are built from the source stop profile:

```python
order = sorted(range(len(src_dep)), key=lambda j: (-src_dep[j], src_ent[j][0]))
```

Sorted latest departure first, breaking ties by earliest arrival.

`_reconstruct_route` follows the pointer chain:

```
board connection → ride → exit connection
    → if KIND_WALK: add walk step to destination, done
    → if KIND_XFER: bisect profile at next_dep, follow next (board, exit, kind), repeat
```

The walk between the query source and the first boarding stop (if different) is prepended from `footpath_secs`.

A route is dropped if:
- Reconstruction fails (broken pointer — should not happen in a correct scan).
- Total walk distance exceeds `max_walk_m`.
- Post-annotation confidence falls below `confidence_q` (the scan uses a per-connection probability estimate; annotation recomputes from reconstructed headways and is more precise).
- The route signature (tuple of step fields) was already emitted.

---

## 8. Post-scan confidence annotation

`_annotate_route_confidence` runs on each surviving route **after** reconstruction. It uses the delay lookup hierarchy (Section 4) rather than the baked array, because the baked array is indexed by connection position while reconstruction produces named steps.

For each ride step:

```
headway = next_step_departure - walk_between - this_step_arrival
       (or deadline_secs for the final ride)

p = P(delay ≤ headway)    # via _delay_quantiles_for_step + _p_leq_headway
```

Route confidence is the product of all step probabilities. A robust arrival time is computed by forwarding predicted delay through the chain:

```python
robust_cursor = arrival_secs + predicted_delay_sec
```

Fields added to each step: `predicted_delay_sec`, `p50_delay_sec` … `p95_delay_sec`, `robust_arrival_time`.

Fields added to the route: `route_confidence`, `passes_confidence`, `per_step_probabilities`, `missed_connection`, `robust_arrival_secs`.

## 9. TTL cache

```python
_route_cache = TTLCache(maxsize=512, ttl=300)
```

`plan()` is decorated with `@cached(..., key=...)`. The cache key is:

```python
(id(self), start_stop_id, end_stop_id, str(travel_date), arrival_deadline,
 max_routes, max_walk_m, search_window_minutes, confidence_q, id(self.delay_lookup))
```

`id(self.delay_lookup)` changes whenever `configure_delay_lookup` is called, automatically invalidating cached results when delay data is updated. The TTL of 300 s limits memory growth in long-running servers.

## 10. Performance characteristics

| Region | Search window | avg | p50 | p95 |
|---|---|---|---|---|
| Lausanne (390 stops, 620k connections) | 120 min | ~58 ms | ~49 ms | ~137 ms |
| All Switzerland (25k stops, 14.5M connections) | 220 min | ~3.7 s | ~3.5 s | ~13 s |

**Bottlenecks by phase:**

- `prepare()` Lausanne: dominated by Trino fetch (~11 s) and materialisation loop (~6 s).
- `prepare()` Switzerland: Trino fetch (~287 s) + materialization (~155 s) + bake (~16 s).
- `plan()` Lausanne: scan dominates; each connection costs ~2 µs (array reads + 2 bisects + 2 `_p_leq_headway` calls).
- Early stopping cuts connections scanned by ~75% on typical queries.

**Memory:**

- `quantiles_a`: 7 floats per connection. Lausanne: ~15 MB. Switzerland: ~300–600 MB.
- Connection arrays: ~5 ints per connection × 8 bytes × 7 days. Switzerland: ~4 GB total (dominated by the struct-of-arrays).

## 11. Public API summary

```python
planner = RobustJourneyPlanner(settings=settings)

planner.prepare(
    regions=LAUSANNE_REGION_UUIDS,  # None = all Switzerland
    travel_date="2026-05-27",       # enables baked-quantile path
    load_delay_lookup=True,         # loads delay artifacts
    rebuild=False,                  # rebuild Trino tables
)

routes = planner.plan(
    start_stop_id=8591818,
    end_stop_id=8591994,
    travel_date="2026-05-27",
    arrival_deadline="18:00",
    confidence_q=0.75,              # P(on-time) threshold per route
    max_routes=5,
    search_window_minutes=120,
)
```

Each returned route dict contains: `departure_time`, `arrival_time`, `n_transfers`, `total_walk_m`, `route_confidence`, `passes_confidence`, `robust_arrival_time`, `steps` (list of ride/walk dicts with per-step delay fields).
